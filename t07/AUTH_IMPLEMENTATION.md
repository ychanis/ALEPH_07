# 과제 7 — 인증 구현 설명서

> 이 문서는 구현과 자동 확인 결과를 기록한다. 실제 사용자 계정 생성·과제 6 기록 연결·실제 5일 사용·사람의 최종 판단은 아직 진행하지 않았다. 테스트 자료는 사용자의 실제 학습 기록으로 계산하지 않는다.

## ① 무엇으로 붙였나

- 방식: 직접 구현한 서버 인증 흐름 + 널리 쓰이는 비밀번호 라이브러리.
- 비밀번호: **bcryptjs 3.0.3**, bcrypt 비용 계수 **12**. salt는 라이브러리가 매번 생성한다. bcrypt 알고리즘을 직접 구현하지 않았다.
- 런타임: Vinext 1.0.0-beta.5 / React 19.2.6 / Cloudflare Workers / D1.
- 인증 상태: 32바이트 암호학적 난수의 서버 세션. 쿠키에는 원래 세션값, DB에는 SHA-256으로 만든 세션값의 지문만 저장한다.
- 만료: 발급 후 **8시간**, 서버에서도 expires와 현재 시각을 비교한다.
- 쿠키: HttpOnly, Secure, SameSite=Strict, Path=/, Max-Age=28800. URL에 세션값을 넣지 않는다.
- JWT 서명키나 별도의 인증 비밀키를 만들지 않는다. 세션값 자체가 비밀이다. 공개 코드에 있는 해시 함수 이름·쿠키 이름은 비밀값이 아니다.

## ② 왜 그걸 골랐나

과제는 로그아웃 뒤 예전 인증값을 재전송해도 거절되는 장면을 요구한다. DB에서 세션 행을 삭제하는 서버 세션을 사용하면 이 동작을 직접 설명하고 확인하기 쉽다. bcryptjs는 기존 Workers/JavaScript 프로젝트에서 사용할 수 있고 계정마다 다른 salt를 자동으로 붙여 준다.

검토했지만 고르지 않은 방법:

- 단순 JWT: 만료 전 토큰을 즉시 차단하려면 별도의 폐기 목록이나 버전 관리가 필요해 서버 세션을 선택했다.
- 외부 인증 서비스: 편리하지만 저장된 비밀번호 해시와 세션 폐기를 이 과제에서 직접 관찰하기 어려워 이번에는 사용하지 않았다.
- SHA-256으로 비밀번호 한 번 해시: 비밀번호 전용의 비용 조절·salt 처리가 없어 사용하지 않았다. SHA-256은 무작위 세션값의 DB 지문에만 쓴다.

## ④ 안 열리는 것을 확인한 기록

### 확인 환경과 원본 기록

- 재현: `node t07/run-checks.mjs` (Node 24 이상, 설치한 의존성 필요).
- 실제 API 소스를 HTTP 서버로 호출하고 SQLite로 D1 인터페이스를 대체했다. 로컬 58항목 PASS, 배포 환경 45항목 PASS를 확인했다. 테스트용 두 계정에 각각 계획과 할 일을 넣었다.
- 요청·응답 전체: **t07/evidence-local.json**. 비밀번호는 `[REDACTED]`, 쿠키는 `pds_session=[REDACTED]`로 기록한다.
- Cloudflare 배포 환경의 확인은 **t07/evidence-live.json**에 별도로 기록한다. 아직 이 파일이 없다면 배포 환경 검증은 완료되지 않은 것이다.
- 테스트 계정은 실제 계정이 아니며 그 비밀번호는 제출하지 않는다. 로컬의 가상 날짜 2~5일차 검증은 기록 흐름만 테스트한 것이며 실제 5일 사용 증거가 아니다. 운영 테스트 계정 두 개는 검증 후 삭제했다.

### 다섯 가지 확인 — 성공과 거절을 나란히

| 확인 | 성공 요청·응답 | 거절 요청·응답 |
|---|---|---|
| 1. 로그인과 인증 필수 | POST /api/auth login, 올바른 테스트 계정 → 200; GET /api/data + 로그인 쿠키 → 200 | 같은 GET /api/data, 쿠키 없음 → 401 `로그인이 필요해요.` |
| 2. 비밀번호·가입 처리 | POST /api/auth signup, 새 아이디 → 201; 맞는 비밀번호 login → 200 | 중복 아이디 signup → 409; 틀린 비밀번호·없는 아이디 login → 모두 401 `아이디 또는 비밀번호를 확인해 주세요.` |
| 3. 기존 세션 폐기 | GET /api/data + 기존 쿠키 → 200 | 로그아웃 후 같은 GET /api/data + **같은 기존 쿠키** → 401. 비밀번호 변경 뒤 기존 쿠키도 401 |
| 4. 계정 간 접근 분리 | GET /api/data?kind=tasks&id=내할일 + 내 쿠키 → 200; 내 자료 생성 POST → 200 | 같은 조회 방식으로 남의 할일 → 404; 남의 할일 수정·삭제 POST → 404. A→B와 B→A 모두 확인 |
| 5. 소유자 위조·내보내기 | GET /api/data + A 쿠키 → A 자료만; GET /api/export + A 쿠키 → A의 JSON | URL·헤더에 B ID를 붙여도 A 자료만. 본문의 owner_id를 B로 넣어 만든 계획도 A 소유. 비로그인 내보내기 → 401 |

계정 간 구체적인 요청:

- 읽기: `GET /api/data?kind=tasks&id=<상대 할일 ID>` + 가린 내 쿠키 → `404 {"error":"자료를 찾을 수 없어요."}`
- 수정: `POST /api/data`, `{"action":"task","value":{"id":"<상대 할일 ID>","plan_id":"<상대 계획 ID>","title":"변조",...}}` → 같은 404.
- 삭제: `POST /api/data`, `{"action":"delete","id":"<상대 할일 ID>"}` → 같은 404.
- 반대 방향도 위 세 요청을 동일하게 수행한다. 실제 ID·요청·응답은 원본 JSON에 있다.
- A→B/B→A의 거절 전후 원래 할 일과 B의 전체 자료가 같음을 deepEqual로 비교했다. B에 새로운 자료를 넣는 요청도 거절했다. 위조 owner_id로 만든 새 계획은 A의 목록에만 있다.

### 저장된 비밀번호

테스트 두 계정은 **같은 테스트 비밀번호**로 가입했다. DB의 bcrypt 값 전체는 evidence-local.json의 `같은 비밀번호·서로 다른 bcrypt salt` 항목에 있다. 두 값이 서로 다르고 `$2b$12$`로 시작하며 입력 원문이 포함되지 않는 것을 assert로 확인했다. hash는 테스트 계정의 값이며 실제 계정의 비밀번호·토큰은 아니다.

코드는 비밀번호와 세션을 console.log로 출력하지 않는다. 로그인 응답에는 비밀번호·해시·쿠키 원문을 JSON으로 반환하지 않는다. 로그인 요청의 네트워크 전송 본문에는 인증에 필요한 비밀번호가 들어간다. HTTPS로 전송하며, 개발자 도구에서 자신이 보낸 본문을 볼 수 있다는 사실까지 숨긴다고 주장하지 않는다. **제출용 요청 기록에서는 반드시 원문을 가린다.**

### 만료·비밀값과 확인 한계

발급 시각 + 8시간을 DB와 쿠키에 설정하고 identity에서 만료를 검사한다. 로컬에서는 테스트 세션의 DB 만료 시각을 과거로 바꿔 401을 확인했다. 실제 8시간을 기다린 운영 테스트라고 주장하지 않는다. 로그아웃은 현재 세션만, 비밀번호 변경은 모든 세션을 끊는다. 다른 기기의 세션까지 모두 끊으려면 비밀번호 변경을 사용한다.

브라우저 번들에는 bcrypt 처리·DB 세션 조회가 들어가지 않고 서버에서 실행된다. 세션은 쿠키 헤더에만 들어간다. 소스와 Git 변경 이력에 새 비밀번호·세션값·서명 비밀키를 넣지 않았다. 자동 테스트 출력도 비밀값을 먼저 가린다. 과거 모든 외부 배포 로그를 열어 전수 검사했다는 주장은 하지 않는다.

## ⑤ AI와 나

- AI에게 맡긴 일: T06 이력 확인·인증 코드·자료 접근 검사·5일 기록 기능·자동 검증·설명서 초안.
- 내가 직접 판단한 일: **실제 사용자가 1일차 질문과 계획 규칙, 3일차 전 변경 이유와 실제 학습 시간을 입력한 뒤 그 판단을 여기 보완한다. 아직 직접 판단했다고 기재하지 않았다.**
- AI 제안을 따르지 않은 일: **사용자 확인 후 작성한다. 없다면 구현·검증 결과를 확인하고 그대로 채택한 이유를 적는다.**

AI가 구현한 코드의 자동 검증과 사람의 실제 확인을 구분한다. 비밀번호는 사용자가 가입 화면에서 직접 정한다.

## ⑥ 아직 못 막은 것

1. 로그인·가입에 속도 제한이나 계정 잠금이 없다. 반복 로그인 시도가 가능하고 bcrypt 연산을 반복시켜 서비스 자원을 소모할 수 있다.
2. 비밀번호 재설정·이메일 소유 확인·2단계 인증이 없다. 비밀번호를 잊으면 복구할 수 없고, 비밀번호가 탈취되면 추가 인증 수단이 없다. 아이디는 이메일 인증을 뜻하지 않는다.
3. 로그인 실패·비정상 접근의 별도 보안 감사 로그와 경보가 없다. 공격을 탐지·추적하기 어렵다.
4. 본격적인 보안 진단·부하 시험·브라우저별 동작 확인을 모두 수행한 것은 아니다. 로컬 API 확인만으로 운영 환경 전체의 안전을 보장하지 않는다.
5. T06에서 이미 공개되었던 자료의 과거 복사본·외부 캐시까지 회수할 수 없다. T07에서는 새 자료와 현재 API 접근을 보호한다.
