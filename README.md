ALEPH 과제 7 · 과제 6의 Plan–Do–See 다이어리를 이어 개발한 프로젝트

계획을 세우고, 실제로 한 일을 기록하고, 결과를 돌아보는 다이어리에 가입·로그인과 계정별 자료 보호 기능을 추가했습니다.
이번 과제에서는 로그인 화면을 만드는 데서 그치지 않고, 서버가 로그인한 사람과 자료의 주인을 확인하도록 구성했습니다. 또한 다른 계정의 자료에 접근하거나 로그아웃한 뒤 이전 인증값을 다시 사용하는 요청이 실제로 거절되는지 확인하고, 그 요청과 응답을 증거로 남겼습니다.

1. 과제 6에서 이어진 기능
기존 다이어리의 계획·할 일·실행 기록·돌아보기 기능을 유지하면서 인증을 추가했습니다.
- Plan: 목표와 기간, 할 일, 예상 시간 등을 정합니다.
- Do: 실제 작업의 시작·끝 시각과 수행 내용, 막힌 이유를 기록합니다.
- See: 예상과 실제를 비교하고, 다음 계획의 개선점을 정합니다.
과제 6에서 저장한 자료는 소유자 확인 후 본인의 다이어리 계정에 연결할 수 있습니다. 기존 기록을 모든 신규 가입자에게 복사하거나 첫 가입자에게 자동으로 넘기는 방식은 사용하지 않았습니다.
과제 6의 제출 당시 commit을 과제 7 Git 이력의 조상으로 보존했습니다. 기존 결과물 주소를 이어 사용하므로 현재 주소에는 과제 7 화면이 표시됩니다. 과제 6 당시 소스는 위의 고정 commit으로 확인할 수 있습니다.

3. 인증 방식과 선택 이유
비밀번호: bcryptjs
bcryptjs 3.0.3을 사용하고, 비용 계수는 12로 설정했습니다. 비밀번호를 평문이나 되돌릴 수 있는 암호문으로 저장하지 않고 bcrypt 해시로 저장합니다.
라이브러리가 매번 다른 salt를 생성하므로 같은 비밀번호로 가입한 두 테스트 계정의 저장값도 서로 다릅니다. 비밀번호 해시 알고리즘 자체를 직접 구현하지 않았고, 가입·로그인·세션 관리 흐름은 직접 구성했습니다.
로그인 유지: 서버 세션
로그인하면 암호학적 난수로 만든 32바이트 세션값을 발급합니다. 브라우저 쿠키에는 세션값을 넣고, DB에는 그 값의 SHA-256 지문을 저장합니다. 서버는 매 요청에서 세션의 존재와 만료 시각을 확인합니다.
설정	값
만료	발급 후 8시간
HttpOnly	브라우저 JavaScript에서 쿠키를 읽지 못하도록 설정
Secure	HTTPS 연결에서 전송
SameSite	Strict
인증값 전달	쿠키 헤더 사용, URL에 넣지 않음


로그아웃하면 DB에서 현재 세션을 삭제합니다. 따라서 브라우저에서 쿠키만 지우는 방식과 달리, 기존 쿠키를 복사해 다시 요청해도 거절됩니다. 비밀번호를 변경하면 해당 계정의 모든 세션을 폐기합니다.
다른 방법과 비교
- 단순 JWT: 만료 전 토큰을 즉시 폐기하려면 추가 관리가 필요하여 서버 세션을 선택했습니다.
- 외부 인증 서비스: 편리하지만 이 과제에서 비밀번호 저장 방식과 세션 폐기를 직접 관찰하고 설명하기 위해 bcryptjs와 서버 세션을 사용했습니다.
- SHA-256으로 비밀번호를 한 번만 해시: 비밀번호 전용 비용 조절 방식이 아니므로 선택하지 않았습니다. SHA-256은 충분히 긴 무작위 세션값의 DB 지문에만 사용합니다.
4. 내 자료만 보이도록 처리한 방법
자료의 주인을 URL·요청 헤더·요청 본문에 적힌 사용자 ID로 결정하지 않습니다. 검증된 서버 세션에서 찾은 사용자 ID를 기준으로 처리합니다.
- 계획 조회에는 owner_id 조건을 적용합니다.
- 할 일·실행·수정 이력·완료·돌아보기는 해당 계정이 소유한 계획과 연결된 자료만 조회합니다.
- 목록 조회와 개별 자료 조회 모두 같은 소유 범위를 적용합니다.
- 수정·삭제 요청에서는 먼저 주인을 확인하고, 확인에 실패하면 변경을 수행하지 않습니다.
- 로그인하지 않은 자료 요청은 401로 거절합니다.
- 다른 계정의 자료 요청은 존재를 감추는 404로 거절합니다.
5. 실제 요청으로 확인한 결과
2026년 10월 6일 구현 검증 시 로컬 58항목, 배포 API 45항목이 통과했습니다. 두 계정에 각각 테스트 자료를 넣고 양방향 접근을 확인했습니다. 배포 환경에서 사용한 임시 테스트 계정은 확인 후 삭제했습니다.
확인 항목	정상 결과	차단·비교 결과
자료 조회	내 쿠키로 내 자료 조회 → 200	쿠키 없이 직접 조회 → 401
계정 분리	내 자료 개별 조회 → 200	A→B, B→A 읽기·수정·삭제 → 모두 404
로그아웃	로그아웃 전 GET 요청 → 200	같은 주소·방식·기존 쿠키로 재요청 → 401
비밀번호 변경	변경 전 기존 세션 → 200	변경 후 기존 세션 → 401
목록·소유자 위조	각 계정의 목록에는 자신의 자료만 포함	URL·헤더·본문의 사용자 ID 위조로 다른 계정 자료에 접근하지 못함
변경 영향	정상 자료 저장 가능	거절 전후 상대 계정 자료와 건수가 동일하고 새 자료도 추가되지 않음
중복 가입	새 아이디 가입 → 201	같은 아이디 재가입 → 409
실패 안내	올바른 계정 로그인 가능	없는 아이디와 틀린 비밀번호의 안내 문구가 동일
전체 내보내기	내 자료 JSON 다운로드 가능	로그인하지 않은 내보내기 요청 → 401

6. 실제 5일 사용과 계획 규칙 변경
로그인한 계정 안에서 서로 다른 Asia/Seoul 기준 실제 날짜 5일을 기록합니다. 1일차에 질문과 계획 규칙을 정하고, 2일차 기록 뒤·3일차 기록 전에 계획 규칙 하나만 변경합니다.
항목	적용 규칙
관찰 지표	하루 집중 학습 시간
단위	분
기록	실제 집중한 정수 분을 하루 한 건으로 저장

합계·평균	일별 분을 더하고 기록일 수로 나눈 산술평균 사용

주 시작	월요일
규칙 변경	한 번만 허용, 변경 시각·이유·1·2일차 기록 ID 저장

현재 실제 사용자는 5일 기록 입력을 마쳤습니다. 다만 내보낸 실제 자료를 바탕으로 날짜·규칙 변경 순서·합계·평균을 대조하고 최종 설명서에 반영하는 작업은 별도로 확인해야 합니다. 이 README에는 확인하지 않은 학습 시간이나 개선 결과를 임의로 적지 않았습니다.
최종 검산은 다음과 같이 합니다.
- 전체 합계: 1~5일차 집중 학습 시간을 더합니다.
- 전체 평균: 전체 합계를 5로 나눕니다.
- 변경 전 평균: 1·2일차 합계를 2로 나눕니다.
- 변경 후 평균: 3·4·5일차 합계를 3으로 나눕니다.
7. 사용 방법
1. 실행 주소를 열어 가입한 뒤 로그인합니다.
2. 기존 다이어리에서 계획·할 일·실행 기록을 관리합니다.
3. 상단의 과제 7 · 5일 기록에서 실제 날짜의 학습 시간과 내용을 남깁니다.
4. 2일차 기록 뒤 계획 규칙 하나를 변경하고 이유를 적습니다.
5. 5일차가 끝나면 화면 합계·평균을 검산하고 전체 내보내기를 합니다.
과제 6 자료 연결은 계정 설정 → 과제 6 소유자 계정 확인 → 기존 기록 연결 순서로 진행합니다. 해당 자료의 소유자 확인과 앱 로그인이 모두 필요합니다.
비밀번호를 바꾸면 다시 로그인해야 합니다. 계정 삭제는 자료까지 함께 지우므로 먼저 전체 내보내기를 해야 합니다.

9. 실행 및 확인
Node.js 24 이상과 Git이 필요합니다. 저장소 루트에서 실행합니다.
npm run install:ci
node t07/run-checks.mjs
node node_modules/typescript/bin/tsc --noEmit
npm run build
위 과정은 코드 검사와 빌드입니다. 운영 서비스처럼 사용하려면 Workers/D1 저장소 및 마이그레이션이 준비되어 있어야 합니다. 단순 HTML 파일을 열거나 GitHub에 올리는 것만으로 서버와 DB가 실행되는 것은 아닙니다.
과제 6 이력 보존 확인:
git merge-base --is-ancestor 42000913e5c7618ee1952557bf9a899d5a7bf058 HEAD
echo $?
결과가 0이면 과제 6 제출 당시 commit이 현재 코드의 조상에 포함되어 있습니다.
